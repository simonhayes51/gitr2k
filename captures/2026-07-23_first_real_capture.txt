BUG FOUND: no COMMAND_SEEN log line ever appeared for SETINFO or
REQMOVES, even though the raw bytes for both were logged in the RECV
packet dump. Root cause: server/connection.py passed each raw recv()
chunk straight to dispatcher.dispatch() as a single blob, and the
dispatcher only looks at the first token in that blob. Since SETINFO and
REQMOVES arrived in the same TCP segment, only SETINFO's handler ever
fired (and only "worked" by accident, because Python's str.split() with
no separator also splits on \r\n, so the "REQMOVES" text got silently
absorbed as extra ignored tokens in setinfo.py's field parsing) -
REQMOVES itself was never dispatched, matched, or logged at all.

FIX: server/connection.py now buffers incoming bytes across recv() calls
and splits on \n before dispatching, so every \r\n-terminated command
gets its own individual dispatch() call no matter how the client batches
multiple commands into one TCP write. Verified locally by replaying the
exact captured byte sequence (including the coalesced SETINFO+REQMOVES
chunk) through the fixed connection-handling logic: all four commands
(MCC, SETPORT, SETINFO, REQMOVES) now dispatch individually and
correctly, with REQMOVES finally reaching commands/reqmoves.py.

Went back to static analysis specifically for REQMOVES/MOVESDB, since
this project had PREVIOUSLY, INCORRECTLY dismissed MOVESDB as an
unrelated Pascal-scripting-engine keyword (grouped with BEGIN/WHILE/
FUNC/SCRIPT/PLUGIN/ACTIONSDB/SWEARDB). Found a real class
"TMovesDBCommand" in arena.exe's string-constant table, directly
clustered with "REQMOVES" and an "invalid response" (16 bytes) error
string - this is a genuine protocol command class, the earlier dismissal
was wrong. A near-identical sibling class references "REQSWLIST"/
"SWEARDB" with the same code shape (likely a swear-word/chat-filter
list), confirming a small family of "request a named database" commands.

Exhaustive raw-bytes cross-reference search (searching for the compiled
string constants' own virtual addresses as literal 4-byte little-endian
values elsewhere in the binary) found exactly one call site each for
REQMOVES and MOVESDB, both inside a single method at arena.exe VA
0x461d34-0x461e92. Disassembling it revealed:

  1. Sends "REQMOVES" via a virtual call (VMT+0x84) - matches confirmed
     wire traffic.
  2. Reads exactly ONE line via a ReadLn-shaped virtual call (VMT+0x74,
     terminator "\r\n") - no loop for further lines, unlike
     RETRCOUNTRIES/RETRARENALIST/METAARENALIST's multi-line responses.
  3. Takes Copy(line, 1, 7) and compares it against the literal
     "MOVESDB" (7 chars) via a CompareStr-shaped call. Mismatch ->
     raises the "invalid response" error found in the string table.
  4. On match, hands the WHOLE line to a further virtual method
     (VMT+0x9c, not disassembled) for parsing - so fields after
     "MOVESDB" remain unknown.

"must" equal the literal "MOVESDB", based on a `je 0x461def` branch after

not the success path.

--- Static analysis (no live test this round): VMT reconstruction reveals REQMOVES is a chained multi-stage sequence ---
Per operator direction ("dig deeper via disassembly" rather than guess
more or switch fronts), went back into arena.exe to find out what the
unexamined VMT+0x9c virtual call in TMovesDBCommand's handler actually
does, instead of leaving it as an unknown "generic parser".

Method: found the compiled Pascal shortstring "TMovesDBCommand" (length-
prefixed, 15 chars) at file offset 0x60d50 (VA 0x461950 for the length
byte). Raw-scanned the whole binary for that VA appearing as a literal
4-byte pointer - found exactly one occurrence, at VA 0x461910. Brute-
forced the actual VMT base by testing every plausible negative offset
from that address, checking which one made ALL FOUR of the offsets
TMovesDBCommand's method actually calls (+0x74, +0x84, +0x9c, +0xC4)
resolve to addresses inside the CODE section. Exactly one candidate fit:
VMT base = 0x461938 (vmtClassName at offset -40/-0x28 for this Delphi
build). This gives VMT+0x9c = 0x461a20.

Disassembled 0x461a20 expecting a data parser - it is NOT one. It's
another near-identical command handler: sends "REQACTIONS" (10 chars),
reads one line, takes Copy(line,1,9), and rejects an EXACT MATCH to the
